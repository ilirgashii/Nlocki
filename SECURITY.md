# Security and privacy of the self-hosted backend

Report suspected vulnerabilities privately to the configured operator contact; do not post secrets or personal data in public issues. This private beta has not had an independent penetration test and must use test data until deployment/legal review is complete.

The default Node/PostgreSQL service uses salted scrypt passwords, encrypted account signing keys/TOTP secrets, hashed random session cookies and recovery codes, exact Host/Origin checks, bounded requests and atomic rate limits. Online mode requires HTTPS and email verification. WebAuthn uses maintained SimpleWebAuthn, origin/RP/challenge and user-verification checks. Adding passkeys or deleting an account requires the current password; passkey sign-in still respects optional TOTP.

TOTP uses six-digit SHA256 / 30-second codes with one-step tolerance and replay protection. Five failed attempts lock verification for five minutes. Protected RPC requires a fresh Ed25519 session key authorized by TOTP/recovery, with signed method/args/time/nonce and replay rejection. Account/cookie alone cannot bypass enabled TOTP. Session keys expire after 30 minutes; revocation tombstones prevent reuse. Photos use the authenticated cookie and its matching 30-minute MFA authorization because image tags cannot supply RPC signatures. XSS/session theft remains a risk; CSP, dependency checks and careful rendering reduce it without eliminating it.

The runtime DB role is not a superuser and cannot bypass document RLS. Queries are parameterized; each RPC applies the account's transaction-scoped RLS context and serializes its writes. Additional API checks sanitize private profiles and limit messages/photos to authorized users. The application service remains trusted: compromising its runtime or the VM host may expose its accessible data. RLS is defense in depth, not protection against every compromised service/admin.

PostgreSQL has no published port in local Compose. Production binds only to a private DB VM IP, requires verified database TLS and exact app-VM firewall/HBA allowlisting. The app origin has no public ports and accepts Cloudflare country headers only behind the tunnel. Geo restrictions are approximate and VPNs can circumvent them. Admin isolation, updates and firewall verification remain the operator's duties.

JPEG uploads are bounded, decoded, resized and re-encoded with metadata removed, placed under random filenames outside the web root and served through access checks. Remote image URLs and unsupported formats are rejected. Quota is 50 MB per account. Detached photos enter a durable deletion queue; account deletion also queues all photos. Cleanup retries failed deletion, so storage failures must be monitored. Orphan files from failed transactions are reconciled after a 24-hour grace period.

Do not commit `.secrets`, encryption keys, dumps, `.dfx`, private photos or TLS private keys. Losing the auth encryption key can make accounts unrecoverable. Backups must be encrypted, independently stored, expired and restored with the latest deletion ledger before reopening. Templates do not install backup automation or provide an audited migration from legacy IC data. See deployment/SELF-HOSTING.md and deployment/GERMANY-PRIVACY.md for prerequisites.

No engineering control or beta agreement certifies GDPR compliance or waives mandatory liability. Operator contact details, processor agreements, legitimate-interest/DPIA assessments, breach response and the deployed system require legal/operational review.

Mobile installation adds only public offline assets to app-controlled Cache Storage. The service worker does not cache API responses, private media, account exports or signed-in records, and offline navigation displays a generic reconnect page. No offline task queue, background sync or push subscription is created. Review this public on-device cache and install behavior with the deployment/privacy review before production.
